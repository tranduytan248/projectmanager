# CODEBASE GUIDE — `khawassco_app`

Reverse-engineered technical reference of this Flutter project, written to be handed to another
Claude Code session as architectural context. It documents **what the code actually does**, traced
through real imports and call sites — not what folder names imply.

---

## 1. Project Overview

**Purpose.** Customer-care mobile app for a Vietnamese water utility (KHAWASSCO / CSKH). Customers
log in by phone number or contract code, view contracts, water-meter readings, invoices, pay online,
submit service requests, read news, and receive push notifications.

**Stack**
- Flutter `3.35.4` (pinned via FVM in `.fvmrc`), Dart SDK `^3.9.2`
- App version `1.0.4+5`, Android applicationId `vn.app.khawassco.cskh`
- State management: **`provider`** (`ChangeNotifier` only — no Riverpod/BLoC/GetX)
- Networking: **`dio`** wrapped in a hand-rolled `HttpManager`
- Local storage: **`shared_preferences`** (key–value) + **`realm`** (offline notification store)
- Push: **`firebase_core` + `firebase_messaging` + `flutter_local_notifications`**
- Misc: `flutter_dotenv`, `crypto` (SHA-256 checksums), `webview_flutter`, `fl_chart`,
  `showcaseview`, `flutter_html`, `pdfx`, `fpdart` (used in exactly one service)

**Architecture in one line.** Feature-first folders over a thin shared core; a screen talks to a
`ChangeNotifier` provider, which calls a feature `Service`, which owns its own Dio client.
There is **no Clean Architecture** here: no `domain/`, no use-cases, no repository interfaces, no
abstract data sources. `Service` is simultaneously the data source and the repository.

## 2. Architecture — Real Dependency Flow

Runtime data flow:

```text
Screen widget (StatefulWidget/StatelessWidget)
  ↓ context.read<X>() / context.watch<X>() / Consumer<X>
Provider (ChangeNotifier)         ← state + orchestration + try/catch + user dialogs
  ↓ direct instantiation:  final s = XService();
Service (per-feature API facade)  ← endpoint + envelope check + JSON → Model
  ↓ owns a field:  final AppHttp _http = AppHttp(baseUrl: ApiEndpoint.baseUrl, headers: {});
AppHttp (request interceptor: Bearer token)
  ↓ extends
HttpManager (Dio instance + global error interceptor + verb wrappers)
  ↓
REST backend (https://cskh.ctnkh.com.vn/)

Side stores, reached directly from providers/helpers (not through Service):
  AppCache → Cache → SharedPreferences        (auth, otp, device token, last-seen dates)
  RealmManager → Realm                        (NotificationModel, UserRealmModel)
```

Navigation flow (a parallel, routing-only stack):

```text
MaterialApp.routes = Routes().routes
  ↓ Routes() = AuthApp().routes + App().routes   (both extend RouteManager)
XController  (StatelessController / ControllerState)   ← the auth guard lives here
  ↓ returns
Display(title:, mobile:, tablet:, desktop: …)          ← responsive breakpoint selector
  ↓
mobile/… Screen widget
```

Notes that matter when reusing this:
- **Provider is both the state manager and the closest thing to DI.** All app-wide notifiers are
  registered once in `lib/config/app_providers.dart`.
- **Services are never injected.** Each `Service` constructs its own `AppHttp` (⇒ its own `Dio`),
  and providers construct services with `new`. The single exception is
  `SupportFeedbackProvider(SupportService())`, injected via constructor at registration.
- **One barrel file, `lib/architect.dart`,** re-exports `core/`, `config/`, `features/`, `models/`.
  Nearly every file imports only `package:khawassco_app/architect.dart`.
- **The network layer shows UI.** The global Dio error interceptor pops dialogs and force-logs-out
  on 401 by itself; providers are not the only error surface.

## 4. Application Startup

`lib/main.dart` — the real order of operations:

1. `WidgetsFlutterBinding.ensureInitialized()`; `Provider.debugCheckInvalidValueType = null`
   (disables Provider's value-type assertion so `Realm` objects can be held in notifiers).
2. `FlutterNativeSplash.preserve(...)` — hold the native splash.
3. `await dotenv.load(fileName: ".env")` — `.env` is bundled as a Flutter asset (`pubspec.yaml`).
4. If not web: `RealmManager.init([UserRealmModel.schema, NotificationModel.schema])` — **must run
   before any Realm access**; `RealmManager.instance` throws otherwise.
5. `SharedPreferences.getInstance()` → read `isFirstLaunch` (decides onboarding vs home).
6. `await FirebaseConfig.init()` — Firebase app, background handler, foreground presentation
   options, iOS permission request, Android channel, FCM device token → `AppCache`.
7. `await FirebaseConfig.initNotification()` — local-notification plugin, `onMessage`,
   `onMessageOpenedApp`, `getInitialMessage` handlers.
8. `runApp(MultiProvider(providers: appProviders, child: CleanApp(...)))`.
9. `_CleanAppState.initState`: remove splash after 500 ms; post-frame, ask for notification
   permission via `DialogService.showConfirm` then `FirebaseMessaging.requestPermission`.
10. `MaterialApp` is built with `navigatorKey` (global, exported from `main.dart`),
    `theme: MyTheme().lightTheme`, `themeMode: context.watch<ThemeProvider>().themeMode`,
    `initialRoute: isFirstLaunch ? App.onboarding : App.home`, `routes: Routes().routes`.

**There is no splash/auth-gate route.** `App.home` is the initial route even when logged out; the
`HomeController` auth guard (`auth => true`) redirects to the login route post-frame.

References: `lib/main.dart`, `lib/config/firebase_config.dart`, `lib/core/classes/realm_manager.dart`

## 5. Core Infrastructure

### 5.1 Networking — `HttpManager` / `AppHttp`

- **Purpose.** Single Dio wrapper offering `get/post/put/patch/delete/download/head/*Uri/
  postMultipart/fetch/request`, plus a global error interceptor.
- **Implementation.** `HttpManager` creates a private `Dio`, sets `baseUrl`/`headers`, and on
  non-web installs an `IOHttpClientAdapter` whose `badCertificateCallback` returns `true`
  (**all TLS certificates are accepted**). `AppHttp extends HttpManager` and adds an `onRequest`
  interceptor that attaches `Authorization: Bearer <token>`.
- **Where initialized.** Never centrally — every `Service` holds
  `final AppHttp _http = AppHttp(baseUrl: ApiEndpoint.baseUrl, headers: {});` (11 instantiations).
- **Error interceptor behaviour** (`HttpManager` constructor):
  - *Network errors* (connect/receive timeout, connection error, `SocketException`): requests are
    de-duplicated per `options.extra['group']` and per `METHOD:uri`. The first failure of a group
    shows one "Mất kết nối" dialog via a `Completer<bool>` lock; concurrent requests of the same
    group wait on that completer instead of stacking dialogs. Groups in use: `dashboard`, `news`,
    `notifications`, `requests`, `support`, `user`, `waterOutage`.
  - *401*: `_forceLogout()` → `AppCache().doLogout()` → `navigatorKey` push to
    `ApiEndpoint.appLoginUrl` clearing the stack → session-expired dialog. Guarded by a static
    `_isLoggingOut` flag.
  - *403 / 404 / 500 / 502 / 503*: `DialogService.showWarning` with a generic message.
- **Important gotcha.** Every verb wrapper is `try { … } catch (e) { log(e); } return response!;` —
  on any throw, `response` is null and the `!` throws a *different* exception. Callers therefore
  see `Null check operator used on a null value`, not the DioException.

References: `lib/core/classes/http_manager.dart`, `lib/config/app_http.dart`

### 5.2 Configuration & Environment

- `.env` (bundled asset) holds exactly one secret: `KEY_PRIVATE`, used for SHA-256 checksums.
- **Base URL is hard-coded** in `ApiEndpoint.baseUrl`, not in `.env`. There are no flavors, no
  build-time `--dart-define`, no staging/prod switch (the staging URL is a commented line).
- `ApiEndpoint` is a static-only class holding every path. Simple paths are `static const`;
  parameterized ones are `static String fn({…})` builders.
- Three URL builders sign their query with SHA-256 over `|`-joined fields plus `KEY_PRIVATE`:
  `eForm(...)`, `paymentOnlineQR(...)`, `electronicInvoice(...)`. These open in a WebView.
- `Config` (`app_config.dart`) holds business constants: hotline, warning threshold, banner count.

References: `lib/config/api_endpoints.dart`, `lib/config/app_config.dart`, `.env`

### 5.3 Authentication

- **Token acquisition.** `doAuth(context, username, password, {remember})` in
  `lib/core/helpers/login_helper.dart` POSTs `form-urlencoded` to `/auth/token` with device token +
  device info, then writes:
  - `auth_data` (via `AppCache.doLogin`) — the "am I logged in" flag,
  - `login_info` (via `AppCache.saveLoginInfo`, **only when `remember == true`**),
  - `otp` (`accountUser`, `idOTP`, `typeAccount`, `phoneMask`).
  Returns `1` success / `0` wrong credentials or throw / `-1` server error.
- **Token usage.** `AppHttp`'s request interceptor calls `loginInfo()` → `AppCache.getLoginInfo()` →
  key **`login_info`** and reads `accessToken`. So the header source and the login flag
  (`auth_data`) are *different* keys — see §16.
- **Route guard.** `StatelessController` / `ControllerState` override `bool get auth => true`;
  `build()` calls `checkLogin(context, auth:, loginUrl:)` which asynchronously checks
  `AppCache.isLogin()` and, post-frame, `Nav.to(context, loginUrl)`.
- **Logout.** `doLogout(context)` clears `auth_data` and re-runs the guard; the interceptor's
  `_forceLogout()` does the same plus a hard navigator reset.
- **Pre-login flow (auth_mod).** `checkAccount` → (existing account) `/login`, or
  (phone) send OTP → `/verifyOTP` → `/resetPassword`, or (contract) `verifyContract` → OTP.
  Orchestrated entirely in `LoginProvider`.

References: `lib/core/helpers/login_helper.dart`, `lib/config/app_cache.dart`,
`lib/config/app_http.dart`, `lib/core/classes/controller_manager.dart`,
`lib/features/auth_mod/providers/login_provider.dart`

### 5.4 Storage

**Key–value (`SharedPreferences`)**
- `Cache` (`core/classes/cache_manager.dart`) — untyped static `saveData/readData/deleteData`;
  supports `int|String|bool` only, silently logs "Invalid Type" for anything else.
- `AppCache` (`config/app_cache.dart`) — semantic layer above it. Objects are stored as
  `jsonEncode`d `Map<String,String>`. Keys in use: `auth_data`, `login_info`, `otp`,
  `device_token`, `last_seen_date_<account>`, plus raw `isFirstLaunch` and
  `has_seen_showcase_main` written directly by `main.dart` / `AppShowcaseProvider`.

**Local database (`realm`)**
- `RealmManager` — lazily-created singleton with generic helpers (`getAll<T>`, `find<T>`,
  `query<T>`, `upsert`, `upsertMany`, `delete`, `deleteMany`, `deleteAllOf`, `clearAll`, `close`).
  `RealmManager.init([schemas])` is called once in `main()`; access via `RealmManager.instance`.
- Schemas: `_NotificationModel` (PK `pk` = `"<notificationId>_<accountUser>"`) and
  `_UserRealmModel` (PK `userId`). Generated `*.realm.dart` files are committed.
- Realm is used **only** for notifications: read-first-then-refresh, with the local `isRead` flag
  preserved across syncs.

References: `lib/core/classes/cache_manager.dart`, `lib/config/app_cache.dart`,
`lib/core/classes/realm_manager.dart`, `lib/models/notification_model.dart`

### 5.5 Routing

- `RouteManager` holds a `Map<String, WidgetBuilder>` with `addRoute` / `addAll` / `routes`.
- Each feature module extends it and registers its own routes **and** exposes its route names as
  `static const String` (`App.home`, `App.invoice`, `AuthApp.checkAccount`, …).
- `Routes()` merges both maps; `MaterialApp.routes` consumes it. All routes are **named, flat, and
  static** — no `onGenerateRoute`, no nested navigators, no route-level type safety.
- `Nav` (same file) is the navigation helper: `Nav.toNamed` (push), `Nav.to`
  (pushReplacement), `Nav.close` (pop).
- **Arguments** are passed as `Object?` and read with
  `ModalRoute.of(context)!.settings.arguments as Map<String, dynamic>` — used by
  `dynamic_webview_controller`, `progress_controller`, `customer_support_screen`,
  `water_outage_schedule_schedule_screen`.
- FCM messages navigate by *name string*: `FirebaseConfig.screenMap` maps `screen_name` payloads to
  widget builders, pushed with `MaterialPageRoute` (bypasses the named-route table);
  `publicScreens` lists the ones reachable while logged out.

References: `lib/core/classes/route_manager.dart`, `lib/config/app_routes.dart`,
`lib/features/main_app/app.dart`, `lib/features/auth_mod/auth_app.dart`

### 5.6 State Management / DI

- `appProviders` (`lib/config/app_providers.dart`) is a `List<SingleChildWidget>` of 11
  `ChangeNotifierProvider`s: `ThemeProvider`, `GlobalStateManager`, `LoginProvider`, `NewsProvider`,
  `InvoiceProvider`, `HomeProvider`, `RequestProvider`, `WaterOutageProvider`,
  `NotificationProvider`, `FAQProvider`, `SupportFeedbackProvider`.
- All are **eagerly-scoped app-wide singletons** (never disposed, never `ProxyProvider`,
  no `lazy: false` overrides, no scoped/per-route providers).
- Provider state convention: private fields + public getters + `notifyListeners()` in a `finally`
  block; loading is a `bool _isLoading/_isLoaded`, errors a `bool _hasError`/`String? _errorMessage`.
- UI reads state with `Consumer<X>` (rebuild scope) or `context.read<X>()` inside callbacks and
  post-frame initializers. `context.watch` appears only in `main.dart` for the theme.

### 5.7 Error Handling

Three coexisting strategies:

| Layer | Mechanism | Where |
|---|---|---|
| Transport | Dio `onError` interceptor → dialogs / force logout / group-locked offline dialog | `HttpManager` |
| Service (dominant) | `if (statusCode 2xx) { ApiResponse.fromHttpResponse(...); if (isSuccess) return data }` → returns `null` / `[]` on failure | all services except `BillService` |
| Service (single outlier) | `Either<Failure, T>` from `fpdart`, with `_handleRequest` wrapper + `_mapDioErrorToFailure` | `BillService` only |

- `Failure` / `ServerFailure` / `NetworkFailure` live in `core/exceptions/network_exception.dart`
  and are referenced only by `BillService` and `HomeProvider.fetchBills` (`result.fold(...)`).
- Providers wrap service calls in `try/catch`, log with `dart:developer log` or `print`, set an
  error flag, and often show a `DialogService` dialog themselves.
- User-facing surfaces: `DialogService` (modal, uses `navigatorKey.currentState!.overlay!.context`
  so it needs no `BuildContext`) and `ToastService` (`fluttertoast`).

### 5.8 Logging

No logging abstraction. A mix of `dart:developer log(...)`, `debugPrint(...)`, and bare `print(...)`
including production paths. Nothing is stripped in release builds.

### 5.9 Base classes and shared UI

- `StatelessController` / `StatefulController` + `ControllerState` — screen wrappers that fold the
  auth guard and the responsive selector into `build()`.
- `Display` — picks between `mobile / mobileLandscape / tablet / tabletLandscape / desktop /
  desktopLarge` by width (576/768/992/1200/1400), wraps in `Title` and a tap-to-dismiss-keyboard
  `GestureDetector`. Only `mobile` is ever supplied in this app.
- `AfterLayoutMixin` — `afterFirstLayout(context)` hook on `State`.
- `core/widgets/` — form fields (`CaTextInputField`, `CaDropdownField`, `CaPickerField`,
  `CaDatePicker`, `CaSearchField`, `PasswordField`, `FileUploadField`), buttons, `CommonAppBar`,
  `CustomBottomNavBar`, `AppTags`, `CustomCard`, `StatusText`, `LineChart`, bottom sheets, dialogs.
- `AppSizes` / `AppColors` / `AppSvg`+`AppImg` — design tokens and asset-path constants.
- `AppShowcaseHelper` / `AppShowcaseProvider` — onboarding tour over `showcaseview`, driven by a
  server config blob and gated by the `has_seen_showcase_main` preference.

## 6. Feature Architecture (two end-to-end walkthroughs)

### 6.1 Notifications — the richest feature (API + Realm + FCM)

```text
App.notifications route
→ NotificationController (auth => true) → Display(mobile: NotificationScreen)
→ NotificationScreen (Consumer<NotificationProvider>)
→ NotificationProvider.fetchNotifications()
      1. read `otp.accountUser` from AppCache
      2. read Realm cache first → notifyListeners()  (instant UI)
      3. getLastSeenDate(account)  (default: 3 days ago, then persisted)
      4. Future.wait([NotificationService.getAllCategories, NotificationService.getAll])
         .timeout(10s)
→ NotificationService → AppHttp.get(ApiEndpoint.notifications(...), extra:{'group':'notifications'})
→ ApiResponse<List<NotificationModel>>.fromHttpResponse(...)
      per item: inject Pk = "<NotificationId>_<accountUser>", default UserAccount,
                NotificationDTO.fromJson → toRealm(dto) → NotificationModel
→ Provider.saveNotificationsToRealm(...)  (preserves the previous `isRead`)
→ reload from Realm, sort desc by createdAt, save lastSeenDate = now
→ notifyListeners() → NotificationScreen + NotificationList + CommonAppBar badge rebuild
```

Side entry point: `FirebaseConfig._refreshNotifications()` calls
`navigatorKey.currentContext.read<NotificationProvider>().fetchNotifications()` whenever an FCM
message arrives or is tapped. `markAsRead` / `markAllAsRead` / `deleteNotification` write straight
to Realm inside `realm.write(...)` and then `notifyListeners()`.

Files: `features/main_app/controllers/main/notification_controller.dart`,
`screens/mobile/notification_screen.dart`, `widgets/notification_list.dart`,
`providers/notification_provider.dart`, `services/notifications_service.dart`,
`models/notification_model.dart`, `models/notification_dto.dart`, `config/firebase_config.dart`

### 6.2 Home dashboard — remote-configured UI

```text
App.home → HomeController → Display(mobile: Home)
→ Home.initState → post-frame → Future.wait([HomeProvider.fetchDashboard(),
                                             NotificationProvider.fetchNotifications()])
→ HomeProvider.fetchDashboard()
   → DashboardService.getAll()   GET /api/dashboard/home?userName&typeAccount
      → dashboardResponseFromJson → DashboardResponse {contracts, clockRecords, invs,

   → DashboardService.getBannerAds()
```

## 7. Data and API Flow

1. **Request creation.** A service method calls `_http.get/post(ApiEndpoint.<something>, …)`.
   Query params are usually already baked into the endpoint string by an `ApiEndpoint` builder;
   `params:` is used rarely. Every call should pass `options: Options(extra: {'group': '<feature>'})`
   so the offline-dialog de-duplication works.
2. **Auth header.** `AppHttp`'s `onRequest` interceptor reads `login_info.accessToken` and sets
   `Authorization: Bearer …`. `AppHttp(useFixedToken: true)` skips this (defined but currently
   unused). Login itself sends `Content-Type: application/x-www-form-urlencoded` explicitly;
   JSON POSTs sometimes set `Content-Type: application/json` per call.
3. **Interceptors.** Exactly two: `AppHttp`'s request interceptor and `HttpManager`'s error
   interceptor. No response interceptor, no logging interceptor, no token refresh, no retry policy
   (the "retry" branch in the group lock is dead code — the completer always completes `false`).
4. **Envelope.** Responses are `{ "status": <http-like int>, "data": <payload>, "message": "…" }`.
   `ApiResponse<T>.fromHttpResponse(response, fromJsonT)` reads `status` (or `Status`), maps `data`
   through `fromJsonT`, and exposes `isSuccess => 200 <= status < 300`. Some endpoints
   (`/api/dashboard/home`) return a bespoke shape parsed directly by `DashboardResponse.fromJson`.
5. **Serialization.** All models are hand-written. JSON keys are **PascalCase** (.NET backend):
   `json["ContractCode"]`, `json["CreatedAt"]`. Dates use `DateTime.tryParse(json[x]?.toString() ??
   '')`; a few still use the throwing `DateTime.parse`. There is **no** `json_serializable`.
6. **Response mapping.** Service returns a domain model, `null`, or `[]`. Only `BillService` returns
   `Either<Failure, T>`.
7. **Repository flow.** None — the provider calls the service directly.
8. **State/UI result.** Provider assigns fields, flips loading flags in `finally`, calls
   `notifyListeners()`; `Consumer` rebuilds. Errors either set a flag rendered as an inline
   retry view (`ConnectionErrorView`) or pop a `DialogService` dialog.

## 8. Important Abstractions


## 9. Coding Conventions

**Naming**
- Files `snake_case.dart`; classes `PascalCase`; private provider fields `_camelCase` with public
  getters. Services end in `Service`, notifiers in `Provider`, route wrappers in `Controller`,
  screens in `Screen` (plus `Home`, `HomeContent` legacy names).
- Route-name constants live as `static const String` on the module's `RouteManager` subclass and are
  built from a `name` prefix: `static const String invoice = '${App.name}/invoice';`.
- Comments and all user-facing strings are Vietnamese; class/member names are English.

**Folder placement**
- Anything business-agnostic → `lib/core/`. Anything app-wide but project-specific → `lib/config/`.
  Feature code → `lib/features/<module>/{controllers,providers,services,screens/mobile,widgets}/`.
  DTOs → `lib/models/` (flat, not per-feature).
- Every folder has a barrel (`widgets.dart`, `services.dart`, …) which is re-exported upward until
  it reaches `lib/architect.dart`. **New files must be added to their barrel** or they will not be
  visible to the rest of the app.

**Imports**
- Import `package:khawassco_app/architect.dart` and nothing else, except third-party packages,
  `package:provider/provider.dart`, and `../../main.dart` for `navigatorKey`. Relative imports are
  used only to break the occasional barrel cycle (e.g. `import '../../screens/mobile/x.dart' as mobile;`).

**Dependency direction**
- `core` must not import `features`. `config` may import `core` and (via `architect.dart`) does
  reach `features` for route constants — this cycle is tolerated because `architect.dart` re-exports
  everything. Providers → services → http/config. Screens never call services directly.

**State handling**
- One `ChangeNotifier` per feature area, registered in `app_providers.dart`.
- Async method shape: set loading + clear error + `notifyListeners()` → `try` service call →
  `catch` log + set error → `finally` clear loading + `notifyListeners()`.
- Screens trigger loads from `initState` inside `WidgetsBinding.instance.addPostFrameCallback`,
  using `context.read<X>()`; they render with `Consumer<X>`.

**API implementation**
- Add the path/builder to `ApiEndpoint` first; never inline a URL at a call site.
- Service method: call `_http.<verb>(endpoint, options: Options(extra: {'group': '<feature>'}))`,
  check `statusCode` 2xx, decode with `ApiResponse<T>.fromHttpResponse`, return data or `[]`/`null`.

**Model conventions**
- Hand-written `factory X.fromJson(Map<String, dynamic>)` + `Map<String, dynamic> toJson()`,
  PascalCase keys, nullable fields with `?`, `DateTime.tryParse(json[k]?.toString() ?? '')`,
  optional `factory X.empty()`. Register the file in `lib/models/models.dart`.
- Realm models: private `_X` class annotated `@RealmModel()` with `part 'x.realm.dart';`, a
  `@PrimaryKey()`, and a `toRealm(dto)` / extension mapper from the network DTO.

**Error handling**
- Default to the status-code + envelope style. Use `Either<Failure, T>` only if you deliberately
  extend the `BillService` pattern.
- Show user errors via `DialogService`/`ToastService`, or set a flag and render an inline retry view.

**DI registration**
- Add `ChangeNotifierProvider<XProvider>(create: (_) => XProvider())` to `appProviders`.
  Services are instantiated inline in the provider method (`final s = XService();`).

**Routing**
- Add a `static const String` to `App`/`AuthApp`, register `addRoute(App.x, (ctx) => XController())`
  in the module constructor, and navigate with `Nav.toNamed(context, App.x, arguments: {...})`.

## 10. How to Add a New Feature

Concrete steps that match the existing code (do not introduce layers that don't exist here):

1. **Model** — create `lib/models/<thing>_model.dart` with `fromJson`/`toJson`; export it from
   `lib/models/models.dart`.
2. **Endpoint** — add a `static const` path or a `static String fn({...})` builder to
   `lib/config/api_endpoints.dart`.
3. **Service** — create `lib/features/main_app/services/<thing>_service.dart`:
   ```dart
   class ThingService {
     final AppHttp _http = AppHttp(baseUrl: ApiEndpoint.baseUrl, headers: {});
     Future<List<Thing>> getAll() async {
       final res = await _http.get(ApiEndpoint.things,
           options: Options(extra: {'group': 'thing'}));
       if (res.statusCode! >= 200 && res.statusCode! < 300) {
         final apiRes = ApiResponse<List<Thing>>.fromHttpResponse(
             res, (json) => (json as List).map((e) => Thing.fromJson(e)).toList());
         if (apiRes.isSuccess) return apiRes.data ?? [];
       }
       return [];
     }
   }
   ```
   Export it from `services/services.dart`.
4. **Provider** — create `providers/<thing>_provider.dart` extending `ChangeNotifier` with private
   state, getters, and the loading/try/catch/finally shape; export from `providers/providers.dart`;
   register in `lib/config/app_providers.dart`.
5. **Screen** — create `screens/mobile/<thing>_screen.dart`; load in a post-frame callback with
   `context.read<ThingProvider>()`, render with `Consumer<ThingProvider>`; export from
   `screens/screens.dart`. Reuse `CommonAppBar`, `core/widgets/forms/*`, `AppSizes`, `AppColors`.
6. **Controller** — create `controllers/main/<thing>_controller.dart`:
   ```dart
   class ThingController extends StatelessController {
     const ThingController({super.key});
     @override bool get auth => true;
     @override Display view(BuildContext context) =>
         Display(title: 'Thing', mobile: const ThingScreen());
   }
   ```
   Export from `controllers/controller.dart`.
7. **Route** — add `static const String thing = '${App.name}/thing';` and
   `addRoute(App.thing, (ctx) => const ThingController());` in `lib/features/main_app/app.dart`.
8. **Entry point into the feature** — either add a `ServiceKey` + `ServiceItemData` entry in
   `config/service_items.dart` (and have the backend include the key in the relevant `CONFIG_*`
   value), or navigate with `Nav.toNamed(context, App.thing)` from an existing screen.
9. **If it needs offline caching** — add a `@RealmModel()` class, register its schema in
   `RealmManager.init([...])` in `main.dart`, and regenerate with
   `dart run realm generate` (or `dart run build_runner build`).
10. **If it must be reachable from a push notification** — add an entry to
    `FirebaseConfig.screenMap` (and to `publicScreens` if it works logged out).

## 16. Technical Debt / Risks

Observed, **not fixed**:

1. **TLS verification disabled.** `HttpManager` installs
   `client.badCertificateCallback = (...) => true` on all non-web builds — every certificate is
   accepted, including MITM ones. `lib/core/classes/http_manager.dart`
2. **Null-check crash instead of error propagation.** Every verb wrapper catches, logs, then does
   `return response!` on a null `response`, converting any Dio failure into
   `Null check operator used on a null value` at the call site. Same file.
3. **Auth token and login state use different cache keys.** The interceptor reads
   `login_info.accessToken`, while `isLogin()`/`doLogout()` operate on `auth_data`.
   Consequences: logging in with `remember: false` deletes `login_info`, so requests go out with no
   `Authorization` header; and after logout the stale token in `login_info` is still attached to
   requests. `lib/config/app_http.dart`, `lib/config/app_cache.dart`, `lib/core/helpers/login_helper.dart`
4. **Credentials stored in plaintext.** `AppCache.doLogin`/`saveLoginInfo` persist the raw
   `password` alongside the token in SharedPreferences. No `flutter_secure_storage`, no keychain.
5. **No token refresh / expiry handling.** `expiresIn` is stored but never consulted; recovery from
   an expired token is a 401 → force logout.
6. **One `Dio` instance per service** (11 total). No connection reuse across services, and
   `connectTimeout`/`receiveTimeout` are never configured — Dio defaults apply.
7. **Dead retry path.** The offline group-lock always completes `false`, so the `shouldRetry`
   branch in the error interceptor can never execute.
8. **Two incompatible error models.** `Either<Failure, T>` exists only in `BillService`; the other
   seven services return `null`/`[]`, silently erasing the failure reason.
9. **The network layer drives UI and navigation.** `HttpManager` shows dialogs and force-navigates
   via a global `navigatorKey`, which makes it untestable and non-portable, and can pop dialogs on
   top of unrelated screens.
10. **Vietnamese copy hard-coded everywhere** (services, providers, interceptors, widgets). No
    localization layer, no `intl` ARB files, no string catalogue.
11. **`GlobalStateManager.doLoad()` is a no-op** — `isLoading != isLoading;` is a discarded
    comparison, not an assignment. `lib/core/classes/global_state_manager.dart`
12. **`print`/`debugPrint` in production paths**, including request payload dumps in
    `ApiEndpoint` (checksums, contract codes) via `debugPrint`.
13. **Duplicated UI/logic.** `HomeScreen._showErrorDialog` re-implements a dialog that
    `DialogService` already provides; `ConnectionErrorView` is defined inside
    `notification_screen.dart` rather than in `core/widgets/`; `LoginController` bypasses
    `StatelessController`/`Display` and builds a `Title` directly; several controllers are
    non-`const` while their siblings are.
14. **`Provider.debugCheckInvalidValueType = null`** in `main()` disables a safety assertion
    globally so mutable Realm objects can live in notifiers — hides real misuse.
15. **Barrel-file cycle risk.** `architect.dart` re-exports everything, so `config` transitively
    depends on `features` (e.g. `ApiEndpoint.appLoginUrl = AuthApp.checkAccount`). A few files must
    use relative imports to compile at all.
16. **Server-config parsing is unguarded.** `HomeProvider.fetchDashboard` uses `.where(...).first`
    on `configKeys`, which throws `StateError` if the backend omits any `CONFIG_MOBILE_*` key;
    `DashboardResponse.fromJson` assumes `contracts`, `clockRecords`, `data`, `configKeys` are all
    non-null.
17. **Mixed date parsing.** Most models use `DateTime.tryParse`, but `ClockRecord.period` and
    `NotificationDTO.createdAt` use throwing `DateTime.parse`.
18. **No tests.** `test/widget_test.dart` is fully commented out; there is no CI configuration in
    the repository.
19. **Dead/unreferenced code.** `packages/payment_package/` has no `pubspec.yaml` or `lib/` and is
    not a dependency; `AppHttp.useFixedToken` is never set to `true`; `initDeepLink()` in
    `main.dart` and the `deep_link_channel` MethodChannel are wired but never enabled;
    `NotificationOutModel` and `NotificationType` appear unused by the current flow.
20. **`webview_flutter` is pinned to an exact version** (`4.9.0`) while its platform
    implementations float (`^3.16.9`, `^3.23.4`) — a resolution hazard.
